# 1. Что и зачем

Проблема. У нативного стейк-аккаунта два полномочия. Staker (ключ стейка) делегирует, снимает с делегирования и делит аккаунт. Withdrawer (ключ вывода) выводит SOL и меняет полномочия. Обычно оба — ключ кошелька пользователя. Кто получил этот ключ (фишинг seed-фразы, малварь) или подсунул пользователю транзакцию со скрытой инструкцией Authorize, тот владеет стейком. Реальные случаи: SwissBorg, 08.09.2025 — 192 600 SOL ушли через скрытую смену права вывода, которую вставил взломанный API стейкинга; MPC-кошельки не помогли. Step Finance, 31.01.2026 — 261 854 SOL. Фишинг seed-фраз у владельцев Ledger в августе 2026.

Наблюдение. В каждом стейк-аккаунте есть Lockup { unix_timestamp, epoch, custodian }. Пока замок действует, для Withdraw и для смены withdrawer нужна ещё и подпись хранителя (custodian). Для Deactivate, делегирования, Split и смены staker она не нужна. Официальная документация говорит, что замок ставится только при создании аккаунта. Код программы (Meta::set_lockup) разрешает withdrawer поставить новый замок на СУЩЕСТВУЮЩИЙ аккаунт, если замок не действует; пока он действует, менять его может только хранитель.

Продукт. Stakeward делает хранителя вторым ключом, который контролирует сам пользователь. Пользователь ставит замок (дата окончания + хранитель = его второй кошелёк) на существующие стейк-аккаунты. После этого вор с основным ключом не может ни вывести стейк, ни переписать его на себя. Владелец получает тревоги и может спасти стейк: перевести оба полномочия на новый кошелёк подписями основного и второго ключа.

Честное ограничение. Второй ключ не двигает деньги, но может поставить замку любую дату и любого хранителя. Кто держит второй ключ, тот может заморозить стейк. Интерфейс, FAQ и карточка восстановления говорят это прямо: второй ключ берегут так же, как основной.

Подача: замок на застейканные SOL на уровне сети, который ставится на уже существующие аккаунты; без хранения чужих средств и без своей программы в сети. Никогда не называть продукт «2FA-кошельком».

Вне рамок: LST-токены, стейк на биржах, vote-аккаунты валидаторов, SOL на обычном балансе.

# 2. Жёсткие ограничения

1. Некастодиальность. Никогда не держим средства пользователей. Никогда не просим, не генерируем за пользователя, не храним и не передаём приватные ключи и seed-фразы. Это написано на каждом экране подписи. (Тестовые ключи для скриптов и тестов лежат в .keys/ и в памяти тестов; это тестовые данные, а не код продукта.)
2. Второй ключ подтверждает себя одним способом: подписывает вместе с основным транзакцию, которую начал пользователь. Подписи сообщений (signMessage) не используем нигде: с Ledger они ненадёжны, и они нам не нужны.
3. Своей программы в сети нет. В транзакциях только инструкции стейк-программы, nonce-инструкции System-программы и Compute Budget. Таблицы адресов (address lookup tables) запрещены. Одно исключение: проверки Lighthouse, которые кошелёк Phantom сам дописывает в конец транзакции (раздел 6).
4. Бесплатно. Без токена и без приёма крипты (автор в Грузии, компаниям там нельзя принимать оплату криптой). Перед каждой подписью показываем комиссию сети: около 0,000005 SOL за подпись; nonce-аккаунт держит около 0,0015 SOL залога, залог возвращается.
5. У каждого необратимого действия есть шаг подтверждения со сводкой простыми словами.
6. Бэкенд не участвует в подписи. Каждую транзакцию собирает браузер из packages/core, подписывают кошельки пользователя, результат сверяется с сетью. Воркер не собирает, не хранит и не подписывает транзакции. Если воркер лежит или взломан, пользователи теряют уведомления, а не деньги.
7. Нет аккаунтов, логинов и сессий. Воркер хранит публичные данные из сети и Telegram chat id, больше ничего.
8. Клиенту не доверяем. Прежде чем что-то сохранить, воркер сам читает аккаунты из сети.

# 3. Устройство системы

Ключи:
  A  основной ключ: withdrawer стейк-аккаунта (обычно он же staker)
  K  второй ключ: хранитель замка (custodian), кошелёк из другой seed-фразы
  D  новый чистый кошелёк, нужен только при спасении

Монорепозиторий pnpm:
  packages/core  чистый TypeScript без ввода-вывода. Декодирование стейк-аккаунтов, правила замка, сборщики транзакций, инспектор транзакций, статус стейка и сравнение снимков. Его используют сайт, воркер, скрипты и тесты.
  apps/web       SPA: Vite + React + TypeScript + Tailwind CSS 4 + shadcn/ui.
  apps/worker    ОДИН Cloudflare Worker: отдаёт собранный сайт как статику, API под /api/*, Cron Trigger, вебхук Telegram, привязка D1. Один домен: нет CORS и нет cookie.
  scripts        проверка механизма, помощники для devnet
  docs           PROGRESS.md, DECISIONS.md, TESTPLAN.md, DESIGN.md, SUBMISSION.md, gate.md

Сайт видит внешний мир через два узких интерфейса. Благодаря им продукт целиком проверяется тестами без настоящих кошельков:
- ChainPort: прочитать аккаунты, эпоху и блокхэш, симулировать, отправить транзакцию, узнать её статус. В продукте его реализует HttpChain поверх /api/rpc, в тестах — LiteSvmChain.
- WalletPort: адрес и «подпиши эти транзакции». В продукте — кошельки Wallet Standard, в тестах — тестовый кошелёк с ключами в памяти.

Библиотеки: @solana/kit 8.4, @solana-program/stake 0.10, @solana-program/system, @solana-program/compute-budget; LiteSVM через @solana/kit-plugin-litesvm; Wallet Standard напрямую (@wallet-standard/app), без провайдеров, которые держат один кошелёк на страницу; Hono; обычный fetch к Telegram Bot API; Tailwind CSS 4, shadcn/ui (примитивы Radix), lucide-react; Vitest, Testing Library, Playwright с axe. Версии точные, без ^; lock-файл в репозитории; установка только с frozen lockfile. Каждая новая зависимость получает строку в docs/DECISIONS.md: зачем она.

Окружения. С первого дня два окружения wrangler: dev (Solana devnet) и prod (mainnet). У каждого своя база D1, свой Telegram-бот и свой адрес RPC. Кластер — это настройка, а не ветка в коде. В dev дополнительно доступны сроки замка 10 минут и 1 час для тестов и демо; в prod их нет. Prod выкатывается в первый же день на постоянном домене, пусть с заглушкой: Phantom помечает новые домены предупреждением и сам снимает его через несколько дней.

RPC. Бесплатный план Helius: 1 млн кредитов в месяц, 10 запросов в секунду; getProgramAccounts — 5 в секунду и 10 кредитов за вызов. Ключ лежит в секретах воркера. Браузер ходит только на свой домен: POST /api/rpc пропускает разрешённый список методов. WebSocket нет: подтверждение транзакции ждём опросом getSignatureStatuses, пока она не подтвердится или не истечёт блокхэш.

Инспектор транзакций — ядро безопасности. Функция inspectTransaction(bytes) в packages/core разбирает транзакцию только из её байтов и возвращает типизированную сводку: вид (protect, extend, unlock, withdraw, rescue, deactivate, delegate, nonce setup), стейк-аккаунт, сумма, новые полномочия, новый замок, плательщик комиссии, срок жизни (блокхэш или nonce), кто должен подписать и чьи подписи уже стоят. Он принимает только формат из раздела 4 и отклоняет любую другую программу, незнакомую инструкцию и таблицу адресов. Для разбора используй parseStakeInstruction из сгенерированного клиента, вручную байты не декодируй. Инспектор работает в трёх местах:
- каждый экран подписи: сводка на экране строится из байтов, которые сейчас уйдут на подпись, а не из состояния приложения;
- /cosign: страница доверяет только байтам и сети;
- прокси RPC в воркере: sendTransaction и simulateTransaction проходят, только если инспектор принял байты. Так прокси нельзя использовать для чужих транзакций.

# 4. Справка по стейк-программе

Сверено 02.10.2026 с репозиторием solana-program/stake (ветка main) и пакетом @solana-program/stake 0.10.0. Источник истины — сгенерированный клиент.

Стейк-аккаунт (StakeStateV2, 200 байт, little endian):
  0    u32  state: 0 Uninitialized, 1 Initialized, 2 Stake, 3 RewardsPool
  4    u64  rent_exempt_reserve
  12   32   staker
  44   32   withdrawer
  76   i64  lockup.unix_timestamp
  84   u64  lockup.epoch
  92   32   lockup.custodian
  124  32   delegation.voter_pubkey
  156  u64  delegation.stake
  164  u64  activation_epoch
  172  u64  deactivation_epoch (u64::MAX = не снимается)
  180  f64  warmup_cooldown_rate (устарело)
  188  u64  credits_observed
  196  u8   stake_flags
Декодируй через decodeStakeStateAccount / fetchAllMaybeStakeStateAccount. Смещения нужны только для фильтров getProgramAccounts.

Поиск аккаунтов: getProgramAccounts по Stake11111111111111111111111111111111111111 с фильтрами dataSize 200 и memcmp по смещению 44 (withdrawer), 12 (staker) или 92 (custodian).

Сборщики инструкций в клиенте. Sysvar-аккаунтов нет; необязательные аккаунты просто не передаются:
  getSetLockupInstruction({ stake, authority, unixTimestamp, epoch, custodian })              каждое значение может быть null = не менять
  getSetLockupCheckedInstruction({ stake, authority, newAuthority?, unixTimestamp, epoch })   newAuthority = новый хранитель, он обязан подписать
  getWithdrawInstruction({ stake, recipient, withdrawAuthority, lockupAuthority?, args })     args = лампорты
  getAuthorizeCheckedInstruction({ stake, authority, newAuthority, lockupAuthority?, stakeAuthorize })
  getDeactivateInstruction({ stake, stakeAuthority }), getDelegateStakeInstruction({ stake, vote, stakeAuthority })
Разбор: identifyStakeInstruction, parseStakeInstruction.
Ошибки: STAKE_ERROR__LOCKUP_IN_FORCE = 1, STAKE_ERROR__MERGE_MISMATCH = 6, STAKE_ERROR__CUSTODIAN_MISSING = 7, STAKE_ERROR__CUSTODIAN_SIGNATURE_MISSING = 8.

Правила из кода программы:
- Замок действует, когда unix_timestamp > clock.unix_timestamp или epoch > clock.epoch. Подпись хранителя снимает его для этой инструкции.
- SetLockup и SetLockupChecked: замок действует -> подписывает хранитель; не действует -> подписывает withdrawer. Иначе MissingRequiredSignature. Хранитель может поставить любую дату и любого нового хранителя.
- Withdraw при действующем замке без хранителя: LockupInForce. Это касается всех лампортов аккаунта, а не только делегированной части.
- Authorize(Withdrawer) при действующем замке: CustodianMissing, если хранитель не подписал; LockupInForce, если подписал не тот ключ.
- Authorize(Staker): подписывает staker или withdrawer. Замок не влияет.
- Deactivate, DelegateStake, Split: достаточно staker. Замок не влияет. Split копирует полномочия и замок в новый аккаунт.
- Merge, MoveStake, MoveLamports: полномочия должны совпадать, замки тоже (или оба не действуют), иначе MergeMismatch.

Итог: вор, у которого только A, может снять стейк с делегирования, переделегировать, разделить аккаунт и сменить staker. Вывести SOL, сменить withdrawer и тронуть замок он не может.

Формат каждой транзакции (только так Ledger показывает её по-человечески, без слепой подписи):
  [AdvanceNonceAccount — если транзакция на nonce]
  [Compute Budget: лимит, затем цена]
  РОВНО одна стейк-инструкция над одним стейк-аккаунтом
Одно исключение — спасение: пара AuthorizeChecked(Staker) + AuthorizeChecked(Withdrawer) для одного аккаунта. В конце допускаются только инструкции Lighthouse от Phantom (раздел 6).

# 5. Правила продукта

- Значения замка: unix_timestamp = T, epoch остаётся 0. K не совпадает с withdrawer, со staker, с самим стейк-аккаунтом и с нулевым ключом.
- Сроки: 1, 3, 6 или 12 месяцев, по умолчанию 6. T = 00:00 UTC после конца периода.
- Досрочное снятие = K ставит unix_timestamp = 0.
- Одна транзакция — один стейк-аккаунт. Несколько аккаунтов = несколько транзакций; подписывать их одним запросом к кошельку, если кошелёк это умеет. Аккаунты независимы: если прошла часть, показать, какие защищены, и дать повторить остальные.
- Комиссию платит основной кошелёк. Исключения: продление и снятие замка платит K; спасение платит D. Скомпрометированный ключ никогда не платит комиссию и не владеет nonce-аккаунтом: бот-свипер выгребает с него SOL, а вор может сдвинуть nonce.
- Compute Budget: фиксированный лимит и небольшая фиксированная цена. Без логики рынка комиссий.
- Статус стейка считаем только по эпохам: activation_epoch == deactivation_epoch -> inactive; deactivation_epoch == MAX -> activating (если activation_epoch >= текущей эпохи) или active; deactivation_epoch >= текущей эпохи -> deactivating; иначе inactive. Математику stake history не переносим. Перед Withdraw настоящая проверка — симуляция транзакции.
- Состояние интерфейса выводится из сети. Страницу можно перезагрузить в любой момент: после перезагрузки она читает аккаунты и показывает правду.
- Что показывает сканер по каждому аккаунту, где адрес — withdrawer:
    замок не действует                              -> Unprotected, можно защитить
    действует, хранитель — ключ этого пользователя  -> Protected until T
    действует, до T меньше 30 дней                  -> Expiring
    действует, хранитель чужой                      -> Locked by someone else, только просмотр
    staker != withdrawer                            -> предупреждение: стейком управляет сервис (например, Marinade Native), с замком он может не суметь слить или перебалансировать аккаунт
  Аккаунты, где адрес только хранитель, идут отдельным списком: «You are the second key for».

# 6. Кошельки и подписи

Что известно (сверено 02.10.2026 по документации Phantom и исходникам приложения Solana для Ledger):
- Phantom может дописать в конец транзакции инструкции Lighthouse (программа L2TExMFKdjpN9kozasaurPirfHy9P8sbXoAN1qA3S95). Для транзакций с несколькими подписями Phantom советует: он подписывает первым через signTransaction, остальные после него. Несколько подписантов и новый домен — известные причины предупреждений в Phantom.
- Ledger разбирает SetLockup, SetLockupChecked, AuthorizeChecked и Withdraw только в формате из раздела 4; иначе требует слепую подпись. Нового хранителя в SetLockupChecked он называет «New authority». Хранителя в Withdraw он не показывает — его показывает наш экран.
- Не проверено: меняют ли транзакцию Solflare и Backpack; как кошельки относятся к durable nonce; отдаёт ли один кошелёк два аккаунта сразу; дописывает ли Phantom Lighthouse для аккаунтов Ledger. Это выясняет матрица на шаге 3, результат идёт в docs/DECISIONS.md и в FAQ.

Правила:
- Подписываем через signTransaction. Отправляет всегда наш сайт.
- Порядок: сначала Phantom, если он участвует, и на ещё не подписанной транзакции; затем плательщик комиссии; затем остальные. Каждый следующий подписывает ровно те байты, что вернул предыдущий.
- После каждой подписи сравнить сообщение с исходным. Допустимо одно отличие: первый подписавший добавил в конец инструкции Lighthouse, которые не добавляют подписантов. Любое другое отличие — остановиться с понятной ошибкой и предложить начать подпись с этого кошелька. Перед отправкой проверить все подписи по итоговому сообщению.
- Три слота по ролям: main, second, new. В каждом один аккаунт Wallet Standard. Слоты занимают разные кошельки или разные аккаунты одного кошелька. Если кошелёк отдаёт только один аккаунт, вести пользователя: «Switch to your second account in the wallet, then press Continue».

Два способа собрать подписи:
- На месте (live): все подписывающие кошельки подключены в этом браузере. Свежий блокхэш. Если блокхэш истёк, собрать заново и повторить.
- По ссылке (link): подписывающие на разных устройствах. Транзакция на durable nonce. Когда плательщик комиссии подписал, id транзакции известен. Частично подписанная транзакция кладётся во фрагмент адреса: /cosign#tx=<байты транзакции в base64url>. Второй подписывающий открывает ссылку или сканирует QR-код, видит сводку инспектора, подписывает и отправляет. Фрагмент адреса не попадает на сервер. Первое устройство ждёт транзакцию по её id. Отменить ссылку можно, сдвинув nonce.

# 7. Сценарии

F1 Защитить
1. Посмотреть аккаунты можно без кошелька: вставить адрес или подключить основной кошелёк. Воркер ищет стейк-аккаунты, где withdrawer = этот адрес.
2. Выбрать аккаунты. Выбрать второй ключ:
   а. Второй кошелёк, подключённый в этом же браузере (рекомендуем; способ «на месте»).
   б. Кошелёк на другом устройстве или доверенный человек (способ «по ссылке»; появляется после шага 7 сборки).
   Отклонять K, равный A или staker. Обязательная галочка: «My second key comes from a different seed phrase».
3. Выбрать срок. Показать: «If you lose the second key, you wait until T. Whoever holds the second key can freeze this stake».
4. На каждый аккаунт своя транзакция: SetLockupChecked { unixTimestamp: T }, authority = A, newAuthority = K. Подписывают оба. Совместная подпись в сети и есть доказательство, что K живой и адрес верный. Других доказательств нет, и в мастере нет пути без подписи K.
5. Симуляция, сводка инспектора, сбор подписей, отправка, подтверждение. По каждому аккаунту свой статус.
6. Перечитать аккаунты и проверить: lockup.unix_timestamp = T, custodian = K. Затем POST /api/watch.
7. Экран «Готово»: подключить Telegram, открыть карточку восстановления.

F2 Мониторинг (cron воркера, раздел 8).

F3 Вывести
1. Активный стейк: Deactivate (подписывает staker), затем таймер до конца эпохи по getEpochInfo.
2. Неактивный: Withdraw всего баланса на основной кошелёк, lockupAuthority = K. Подписывают A и K, на месте или по ссылке.
3. Предупреждение на этом экране: «If your main key may be compromised, do not withdraw to it. Use Rescue».
4. Запасной путь: K снимает замок досрочно (F5), затем основной кошелёк выводит один в любом кошельке. Предупредить, что так открывается окно для вора.

F4 Спасти (основной ключ украден)
1. Пользователь создаёт новый кошелёк D с новой seed-фразой и подключает его. На D нужно около 0,01 SOL: проверить баланс и подсказать, откуда перевести.
2. Заново найти все стейк-аккаунты с withdrawer = A, включая новые после Split.
3. D создаёт nonce-аккаунт (D — его authority). Спасение всегда идёт через nonce: три подписи не должны гоняться за блокхэшем, который живёт минуту.
4. На каждый аккаунт своя транзакция: AuthorizeChecked(Staker -> D) с подписями A и D (работает, даже если вор сменил staker, потому что A всё ещё withdrawer), затем AuthorizeChecked(Withdrawer -> D) с подписями A, D и K. Комиссию платит D. По одному аккаунту за раз: каждая транзакция сдвигает nonce.
5. Подписи собираются с кошельков, подключённых здесь, или по ссылке. Отправить и проверить в сети: staker = withdrawer = D, замок не изменился.
6. Предложить снова делегировать снятые аккаунты (подписывает D) и закрыть nonce-аккаунт.

F5 Продлить или снять замок: K подписывает SetLockup { unixTimestamp: T2 } (0 = снять). Комиссию платит K; если на K нет SOL, платит и подписывает вместе с ним основной кошелёк.
F6 Срок истёк: основной кошелёк защищает заново (F1). Страница аккаунтов показывает красный баннер, пока аккаунт, который был защищён, стоит без замка.
F7 (необязательно) Сменить второй ключ: K подписывает SetLockupChecked с newAuthority = K2; K2 подписывает вместе с ним.
F8 (необязательно) Хранилище Squads как второй ключ: пользователь вставляет адрес хранилища; PDA не может подписать здесь, поэтому это единственное место для SetLockup без подписи хранителя, за подтверждением, которое нужно набрать руками. Продление и снятие замка = инструкция SetLockup, выгруженная для предложения в Squads. Вывод = снять замок через Squads, затем основной ключ выводит один.

- Декодировать и сравнить с сохранённой строкой функцией сравнения из packages/core. Записать события одним batch-запросом; ключ UNIQUE не даёт дублей. Типы: DEACTIVATED, DELEGATION_CHANGED, STAKER_CHANGED, WITHDRAWER_CHANGED, LOCKUP_CHANGED (продлён, укорочен, снят, сменился хранитель), BALANCE_DECREASED, ACCOUNT_CLOSED, EXPIRED.
- После DEACTIVATED, STAKER_CHANGED и BALANCE_DECREASED в этом же проходе заново искать аккаунты этого withdrawer, чтобы поймать Split; новые аккаунты с действующим замком берутся под наблюдение автоматически.
- Отправить события с notified_at = null в чаты, привязанные к withdrawer аккаунта (до и после изменения) и к хранителю. Не больше 25 отправок за проход. Не ушло — notified_at остаётся пустым, повтор на следующем проходе. Telegram ответил 403 (бота заблокировали) — удалить привязку.

UX-правила. Пользователей трое: владелец крупного стейка на Ledger, который не разработчик и боится потерять деньги; валидатор или команда, которым важны скорость и CLI; держатель второго ключа, которому пришла ссылка и который не знает контекста.
1. Сначала посмотреть, потом подключать. Проверить свой стейк можно по адресу, без кошелька. Кошелёк просим в момент действия.
2. Один главный шаг на экране. Мастер показывает шаги и где ты сейчас; «Назад» не теряет введённое.
3. Перед подписью: что было и что станет, кто подписывает, сколько стоит и чего эта транзакция сделать не может («This transaction cannot move your SOL»). Плюс строка «Stakeward never asks for your seed phrase».
4. Роли ключей везде называются одинаково: Main key, Second key, New wallet. Слов custodian и withdrawer в интерфейсе нет, они есть только в FAQ и карточке восстановления.
5. Статус виден словом, цветом и значком сразу, не только цветом.
6. Риск говорится до действия, простыми словами и с датой: «If you lose the second key, you wait until 12 April 2027».
7. Ожидание всегда объяснено: ждём кошелёк, отправляем, подтверждаем. У каждого ожидания есть выход.
8. Ошибка говорит, что случилось и что делать дальше; исходный текст ошибки спрятан под «Details». Тупиков нет. Ошибки программы переведены, например LockupInForce -> «Locked until <date>: your second key must co-sign».
9. Адреса: на экране подписи целиком, в остальных местах сокращённо, с копированием и ссылкой на эксплорер. У каждой транзакции ссылка на эксплорер.
10. Работает на ширине 360 пикселей. Во встроенном браузере мобильного кошелька доступен только этот кошелёк, поэтому там работают просмотр, действия с одной подписью (продлить, снять замок) и /cosign; остальное — на десктопе, и об этом сказано на экране.
11. Доступность: всё делается с клавиатуры, фокус виден, контраст не ниже AA, анимации уважают prefers-reduced-motion.
12. Доверие: на каждой странице ссылки на исходный код и на раздел «What Stakeward cannot do»; страница аккаунтов показывает «Last checked N min ago» по /api/health, красным после 10 минут.
13. Пустые состояния объясняют: нет стейк-аккаунтов — чем нативный стейк отличается от LST и что мы защищаем.

Прочее:
- Все строки интерфейса лежат в src/i18n/en.json (русский позже).
- /cosign читает транзакцию из фрагмента адреса, прогоняет инспектор, загружает текущее состояние стейк-аккаунта и показывает «было -> станет». Красное предупреждение, если новый владелец или получатель вывода не входит в число кошельков, подписывающих эту транзакцию.
- Карточка восстановления (CSS для печати): аккаунты, оба ключа, дата окончания, что делать в каждом случае и команды Solana CLI, которые работают без Stakeward (withdraw-stake --custodian, stake-authorize --custodian, stake-set-lockup). Секретов в карточке нет.

 9. Merge S1 с незапертым аккаунтом с теми же полномочиями: ожидаем MergeMismatch.
10. Withdraw из запертого неделегированного аккаунта с подписями A и B: ожидаем успех.

# 11. Безопасность

Угрозы, которые закрываем: кража основного ключа; фишинговая транзакция со скрытым Authorize; кража второго ключа (вор может заморозить стейк, но не забрать); оба ключа из одной seed-фразы; забытое продление; взломанный сайт или сервер Stakeward; украденный токен Telegram-бота; фишинговая ссылка /cosign, присланная держателю второго ключа; поддельный сайт Stakeward, который ставит хранителем вора; подмена зависимости в npm.
Обязательно:
- Экран подписи показывает сводку инспектора по тем самым байтам; подписанная транзакция проверяется по правилам раздела 6.
- При спасении новый владелец — подключённый кошелёк D, адрес показан целиком, и D обязан подписать (AuthorizeChecked).
- Скомпрометированный ключ не платит комиссию и не владеет nonce-аккаунтом.
- Заголовки на всех ответах (для статики — файл _headers, для /api — в Hono): Content-Security-Policy с default-src 'self', script-src 'self', connect-src 'self', img-src 'self' data: (значки кошельков), frame-ancestors 'none', base-uri 'none', form-action 'none', object-src 'none'; Referrer-Policy: no-referrer; X-Content-Type-Options: nosniff; Strict-Transport-Security. Никаких сторонних скриптов, шрифтов и аналитики. Если Radix потребует inline-стили, разрешить только style-src-attr и записать это в DECISIONS.md.
- В коде сайта нет dangerouslySetInnerHTML. Всё, что пришло из сети или из ссылки, выводится как текст.
- Зависимости: точные версии, frozen lockfile, `pnpm audit` в GitHub Actions; обновление версии — отдельный коммит с причиной.
- В тревогах ссылки только на домен Stakeward. Домен написан в README и в описании бота.
- В сборке сайта нет секретов; ключ Helius и токен бота лежат в секретах воркера.
- Поиск по коду не находит полей ввода и путей кода для seed-фраз и приватных ключей нигде, кроме scripts/ и тестов. Тестовый кошелёк не попадает в сборку prod; это проверяет тест.
- Репозиторий открыт (MIT), в подвале сайта и в README — «No warranty».

# 12. Надёжность

- Правда — в сети. Сайт и воркер после каждого действия перечитывают аккаунты; ничего не считается сделанным по одному только ответу кошелька или RPC.
- Запросы к RPC: таймаут 8 секунд, до двух повторов для чтения. Повторная отправка тех же подписанных байтов безопасна, новая подпись при этом не нужна.
- Запасной адрес RPC для чтения задаётся настройкой; при отказе основного воркер пробует его.
- Каждое ожидание на сайте конечно: по истечении времени показать, что случилось, и дать повторить.
- Мониторинг переживает сбой: следующий проход начинает с курсора, события не теряются и не дублируются.
- Ошибки воркера уходят в ADMIN_CHAT_ID; /api/health можно отдать внешнему пингу.
