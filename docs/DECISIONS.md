# Решения

Каждое решение: дата, что решили и почему. Расхождения с CLAUDE.md записываются сюда же.

## D1. Ledger: устаревший порядок аккаунтов (02.10.2026)

Withdraw, AuthorizeChecked, Deactivate и DelegateStake собираем в старом (legacy) порядке аккаунтов: в инструкцию от `@solana-program/stake` 0.10.0 вставляем sysvar-аккаунты (Clock, для Withdraw и DelegateStake ещё StakeHistory, для DelegateStake ещё StakeConfig). Ledger понятно показывает только этот порядок. С новым порядком без sysvar он требует слепую подпись, а для AuthorizeChecked с хранителем показывает не те ключи. SetLockup, SetLockupChecked и Split в обоих порядках одинаковы. Программа в сети принимает оба варианта.

Это расходится с CLAUDE.md §4 («Sysvar-аккаунтов нет»). Инспектор (шаг 2) принимает только наши форматы. Порядок в сети подтверждает проверка механизма на шаге 1.

Подтверждено на LiteSVM с программой v5.1.0 (02.10.2026): все четыре инструкции в старом порядке выполняются (`packages/core/test/builders.svm.test.ts`). Devnet и mainnet подтвердит проверка механизма. Позиции sysvar записаны в `LEGACY_SYSVAR_SLOTS` (`packages/core/src/legacy-layout.ts`), по этой же таблице инспектор проверяет и убирает sysvar перед `parseStakeInstruction`.

- В tsconfig включены `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, `erasableSyntaxOnly`. `baseUrl` TS 6 не принимает, поэтому алиас `@/` задан только через `paths`, а Vite читает его сам (`resolve.tsconfigPaths: true`).

## D3. CSP и Radix (02.10.2026)

Оставляем Radix (shadcn, база radix) и строгую CSP из §11 без послаблений. Не используем примитивы Radix, которые вставляют элемент `<style>`: Dialog, AlertDialog, Select, Sheet, модальные Popover и DropdownMenu (их блокирует `style-src 'self'`, ломается блокировка прокрутки). Модальные окна делаем на нативном `<dialog>`. Действует с шага 3.

## D4. Стейк-программа в тестах LiteSVM (02.10.2026)

Тесты загружают сборку v5.1.0, она побайтно совпадает с релизом на GitHub и с программой в mainnet: sha256 `3d2d39c596ce8be2d47816b4ee5db9fc759d80fde54b08c930ad0b6daed64c2c`, 212 056 байт. Файл лежит в `packages/core/test/fixtures/programs/stake-v5.1.0.so`, рядом README с источником и хешем. 02.10.2026 файл заново скачан с релиза program@v5.1.0 на GitHub, sha256 совпал. Харнесс `test/svm.ts` сверяет хеш перед загрузкой, а тест сравнивает programdata в LiteSVM с файлом.

## D5. Lighthouse от Phantom и Ledger (02.10.2026)

Ledger отказывается разбирать транзакцию, если в ней есть незнакомая ему программа. Значит, хвост Lighthouse, который дописывает Phantom, переводит Ledger в слепую подпись. Насколько это бьёт по пользователям Ledger через Phantom, меряем в матрице кошельков на шаге 3.

## D6. RPC: всегда base64 (02.10.2026)

В каждом запросе явно передаём `encoding: 'base64'`. Публичные узлы отклоняют кодировку по умолчанию (base58) для 200-байтных аккаунтов: getProgramAccounts отвечает `-32602`, getAccountInfo — `-32600`.

## D7. Минимальная делегация 1 SOL (02.10.2026)

Минимум делегации 1 SOL в mainnet, devnet и LiteSVM. Для scripts/dev-accounts.ts нужно от 3 SOL на devnet. Проверке механизма на devnet хватает 1,01058496 SOL (D21): S1 держит ровно минимум делегации, а Split идёт уже по неактивному аккаунту.

Поправка на шаге 3: dev-accounts с параметрами по умолчанию нужно 1,10399392 SOL, а не 3 SOL (D43).

## D8. Скрипты запускаются обычным Node 24 (02.10.2026)

`node check-rpc.ts` работает без tsx: Node 24 сам вырезает типы. Импорт `@stakeward/core` тоже работает, потому что pnpm кладёт пакет симлинком, его настоящий путь вне `node_modules`. Условия: только стираемый синтаксис и `.ts` в относительных импортах, это проверяют `erasableSyntaxOnly` и `allowImportingTsExtensions`. На одну зависимость меньше.

## D9. Воркер и wrangler (02.10.2026)

- Окружения `dev` (devnet, воркер `stakeward-dev`) и `prod` (mainnet, воркер `stakeward-prod`). У каждого своя база D1. `database_id` в wrangler.jsonc — заглушки, их заменяет владелец после `wrangler d1 create stakeward-dev` и `wrangler d1 create stakeward-prod`.
- Верхний уровень wrangler.jsonc — только локальные значения по умолчанию (`CLUSTER=devnet`, база `stakeward-local` с нулевым id). Без них `wrangler types` делает `env.DB` и `env.CLUSTER` необязательными. Деплой без `--env` упадёт на несуществующей базе, так и задумано.
- `compatibility_date` = 2026-08-15. Пул тестов (vitest-pool-workers 0.22.0) везёт свой workerd, а тот понимает даты не новее 2026-08-22. Поднимать дату вместе с пулом.
- Секреты (`RPC_URL`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `ADMIN_CHAT_ID`) описаны в комментарии wrangler.jsonc, но пока не объявлены в `secrets.required`: с этим полем первый деплой нового воркера падает, если секреты не заданы. Объявим, когда код начнёт их читать. На шаге 3 `RPC_URL` объявлен (D40).
- Cron появится на шаге 5.
- Воркер зависит от `@stakeward/web` (workspace, dev): так `pnpm -r build` собирает сайт раньше воркера, а `wrangler deploy --dry-run` требует готовый `apps/web/dist`.
- `worker-configuration.d.ts` (типы из `wrangler types`, 612 КБ) лежит в репозитории, CI проверяет его свежесть через `wrangler types --check`.

## D10. Заголовки безопасности (02.10.2026)

Для статики заголовки задаёт `apps/web/public/_headers`, для `/api/*` — `secureHeaders` из Hono с теми же значениями. Тест воркера читает `_headers` и сверяет каждое значение с ответом API, так что разъехаться им не дадут. CSP ровно из §11, с `style-src 'self'`. У API остаются и остальные заголовки Hono по умолчанию (Cross-Origin-Opener/Resource-Policy, X-DNS-Prefetch-Control и др.), `X-Frame-Options` выставлен в `DENY` под `frame-ancestors 'none'`. Локальная проверка через `wrangler dev`: `/`, `/app` и отсутствующий `/assets/missing.js` отдают index.html со всеми четырьмя заголовками, `/api/health` и `/api/nope` — JSON с заголовками из Hono.

## D11. pnpm: сборки, возраст пакетов, audit (02.10.2026)

- `allowBuilds: { esbuild, workerd }` в pnpm-workspace.yaml: pnpm 12 по умолчанию запрещает install-скрипты, а этим двум пакетам нужен postinstall.
- `minimumReleaseAge` оставили по умолчанию (1 день). Пакеты моложе суток pnpm сам дописывает в `minimumReleaseAgeExclude`; этот список коммитим.
- `pnpm audit` на чистой установке нашёл 11 уязвимостей (3 high) в undici 7.29.0 и sharp 0.35.2. Оба пришли через `@cloudflare/vitest-pool-workers` (он закрепил старые miniflare и wrangler 4.124.0), то есть только в тестовой цепочке. Закрыли патч-версиями через `overrides`: `undici@<7.29.1 → 7.29.1`, `sharp@<0.35.4 → 0.35.4`. После этого `No known vulnerabilities found`, тесты воркера проходят. Убрать overrides, когда выйдет новый pool-workers.

## D13. Срок замка (02.10.2026)

T считается так. К `now` (UTC) прибавляем N календарных месяцев. Если такого дня в целевом месяце нет, берём последний день месяца: 31 января + 1 месяц = 28 или 29 февраля. Время суток сохраняется. T — первая 00:00 UTC строго после этого момента, то есть начало следующих суток; ровно в полночь тоже переносим на следующую. Сроки 10 минут и 1 час доступны только при `cluster = 'devnet'`: `lockPeriodsFor('mainnet')` их не отдаёт, `lockupEnd` на mainnet бросает ошибку. Кластер передаёт вызывающий, core окружение не читает.

## D14. Статус в сканере (02.10.2026)

По данным сети нельзя понять, чей ключ стоит хранителем. Поэтому `scannerStatus(account, secondKeys, clock)` принимает список вторых ключей, которые известны для этого пользователя: кошелёк в слоте second, хранители, которых он уже подтвердил. Хранитель не из списка — Locked by someone else. Откуда брать список на `/app?address=` без кошелька, решаем на шагах 3–4. Решено на шаге 3: D35.

Замок, у которого хранитель — сам withdrawer, считается Unprotected: основной ключ снимает его один, а защита на таком аккаунте работает (A подписывает как хранитель). Замок, который действует только по эпохе, не бывает Expiring. Отдельного параметра `now` нет: текущее время — `clock.unixTimestamp`.

## D15. Проверка типов в core (02.10.2026)

`packages/core/tsconfig.json` проверяет только `src`, без типов Node и DOM: в коде продукта нет ввода-вывода. Тесты и харнесс LiteSVM проверяет отдельный `test/tsconfig.json` с типами Node и библиотекой DOM. DOM нужен потому, что типы подписантов kit ссылаются на глобальный `CryptoKeyPair`, а в @types/node он есть только внутри `webcrypto`. Тестовый кошелёк с ключами в памяти лежит в `packages/core/test/wallet.ts`, код продукта его не импортирует.

## D16. Compute Budget: фиксированные лимит и цена (02.10.2026)

Для всех видов транзакций лимит 60 000 CU и цена 10 000 микролампортов за CU (`COMPUTE_UNIT_LIMIT`, `COMPUTE_UNIT_PRICE_MICRO_LAMPORTS` в `packages/core/src/constants.ts`). Приоритетная комиссия при таком лимите не больше 600 лампортов, на фоне 5000 за подпись это мелочь.

## D17. Только legacy-сообщения (02.10.2026)

Все транзакции собираются как legacy-сообщения, не v0. Таблицы адресов запрещены (§2), а без них v0 ничего не даёт и длиннее на 2 байта. Legacy понимают все кошельки и Ledger. Инспектор принимает только legacy.

## D18. Nonce-аккаунт через CreateAccountWithSeed (02.10.2026)

Nonce-аккаунт создаётся инструкцией System CreateAccountWithSeed: base и плательщик — сам D, seed — строка `stakeward-nonce`. Адрес выводится из (D, seed, System program), это делает `deriveNonceAccountAddress`. С обычным CreateAccount новый аккаунт обязан подписать сам, и браузеру пришлось бы генерировать для него одноразовый ключ. С seed подписывает только D, лишних ключей нет.

Ledger показывает пару CreateAccountWithSeed + InitializeNonceAccount так же, как CreateAccount + InitializeNonceAccount: «Create nonce acct» (LedgerHQ/app-solana, `libsol/transaction_printers.c`, `is_create_nonce_account_with_seed`). Seed здесь — метка для вывода адреса, а не ключ и не seed-фраза. У одного D один nonce-аккаунт с этим seed; после закрытия его можно создать снова по тому же адресу. На LiteSVM проверены создание, спасение на этом nonce и закрытие.

## D19. Значения замка в транзакциях (02.10.2026)

Защита (SetLockupChecked) передаёт unixTimestamp = T и epoch = None, то есть «не менять». У обычных аккаунтов epoch замка и так 0, а Ledger без epoch не показывает лишнюю строку. Продление и снятие (SetLockup от K) меняют только unixTimestamp; epoch и custodian передаются как None.

## D20. Один сборщик на все виды транзакций (02.10.2026)

`buildTransaction(action, { feePayer, lifetime })` вместо отдельной функции на каждый вид. `action` (`TransactionAction` в `packages/core/src/actions.ts`) — то же описание, которое вернёт инспектор, поэтому проверка «сводка совпадает с тем, что подали в сборщик» сводится к сравнению объектов. Ключи в сборщике — только адреса (`createNoopSigner`), подписывают кошельки. Плательщика по §5 даёт `expectedFeePayer(action)`; для продления и снятия вызывающий может явно передать основной ключ (F5). Withdraw допускает `secondKey: null` для вывода после снятия или окончания замка. Спасение всегда требует K.

## D21. Проверка механизма: устройство прогона (02.10.2026)

- `runGate(chain, { cluster, keys })` в `scripts/gate/run.ts`, два адаптера: LiteSVM (`gate/litesvm.ts`, поверх харнесса `packages/core/test/svm.ts`) и RPC (`gate/rpc.ts`). RPC-адаптер шлёт транзакцию в base64 без preflight, потом опрашивает getSignatureStatuses до `confirmed` или до истечения блокхэша; на 429, 5xx и обрыв соединения повторяет запрос с паузой. Публичный devnet отвечает 429 уже на опрос раз в секунду.
- Всё, что отправляет и продукт (delegate, protect, withdraw, extend, unlock, deactivate, rescue, создание и закрытие nonce), собирает `buildTransaction` из core. Чего в продукте нет (AuthorizeChecked вора, Split, Merge), гейт собирает в том же формате: лимит и цена CU, одна стейк-инструкция, legacy-сообщение, AuthorizeChecked в legacy-порядке аккаунтов.
- Проверки, которые должны упасть, в devnet и mainnet уходят без preflight: транзакция попадает в блок с ошибкой, и у неё есть подпись в эксплорере. Это стоит одну комиссию.
- S1 делегируется (1b) и снимается с делегирования (7a) в одной эпохе. Такая делегация сразу неактивна, поэтому Split и Merge на шагах 8–9 не упираются в минимум делегации и прогрев, а S1 в конце выводится сразу. На devnet скрипт не стартует, если до конца эпохи меньше 20 минут.
- Стейк-аккаунты создаются через CreateAccountWithSeed от плательщика, seed содержит метку прогона. Одноразовые ключи для аккаунтов не нужны.
- На devnet ключи A, B, X, D генерируются на каждый прогон и сохраняются в `.keys/gate-devnet-{a,b,x,d}.json`; на mainnet в `.keys/mainnet-gate-{b,x}.json`, A — сам одноразовый ключ, D не нужен. В начале прогона скрипт возвращает плательщику всё, что осталось на ключах прошлого прогона; если вернуть не вышло, старые файлы переименовываются, а не затираются. В конце прогона всё, кроме комиссий, возвращается плательщику.
- На mainnet продление и снятие замка оплачивает A, как в F5, когда у K нет SOL. Так ключу B не нужен баланс.
- Сумма пополнения считается точно: залоги за аренду из сети, 1 SOL минимума делегации, комиссия каждой транзакции (5000 лампортов за подпись плюс 600 приоритетной) и остаток, без которого кошелёк не может платить комиссию. План транзакций по плательщикам лежит в `gate/budget.ts`. Тест `scripts/gate/gate.test.ts` прогоняет планы всех трёх кластеров на LiteSVM ровно с этой суммой и проверяет, что в конце у плательщика осталась сумма минус комиссии. Devnet: 1,01058496 SOL, из них комиссии 0,0002624. Mainnet: 0,00238128 SOL, комиссии 0,0000648.
- Харнесс core отдаёт скриптам `@stakeward/core/test/svm`, `test/wallet` и `test/support`. В `test/support.ts` нет LiteSVM: там фикстура программы и перевод `SolanaError` в данные с именами ошибок рантайма, им пользуются и харнесс, и RPC-адаптер.

## D22. Аренда в mainnet и devnet: 5080 лампортов за байт (02.10.2026)

Rent sysvar в mainnet и devnet отдаёт `lamportsPerByte` 5080 (порог освобождения от аренды уже учтён). Минимум без аренды: кошелёк 650 240 лампортов, nonce-аккаунт 1 056 640 (около 0,00106 SOL, а не 0,0015, как в CLAUDE.md §2), стейк-аккаунт 1 666 240. Старые аккаунты хранят прежний `rent_exempt_reserve` 2 282 880. LiteSVM 1.5.0 по умолчанию считает 6960 за байт, харнесс `TestChain` ставит 5080, чтобы тесты шли с той же арендой, что и сеть. Залог на экранах и в FAQ берём из сети (getMinimumBalanceForRentExemption), а не константой.

## D23. Инспектор транзакций (02.10.2026)

- Порядок проверок, первая упавшая задаёт код: строгое декодирование → белый список программ (Lighthouse только хвостом) → разбор каждой инструкции (identify, точное число аккаунтов, позиции sysvar для legacy-порядка, parse, перекодирование данных и сравнение с исходными байтами) → последовательность `[AdvanceNonce]? [лимит CU] [цена CU] действие` с точными константами CU → допустимые параметры → точные роли аккаунтов → контрольная пересборка через `buildTransaction` → подписи.
- Строгое декодирование отклоняет как `malformed`: неканонические байты, не-legacy сообщение, кривой заголовок, повтор аккаунта, индекс за пределами списка, число слотов подписей не равно числу подписантов, больше 1232 байт.
- Контрольная пересборка делает правила сборщика правилами инспектора: разные ключи, положительные суммы, T не позже 01.01.2100 (`MAX_LOCKUP_END`), единственный seed nonce-аккаунта, правила спасения. Отказ сборщика → `unknown-instruction`; почти-пара спасения → `multiple-stake-accounts`.
- Сводка не знает контекста сети. Экраны и /cosign сравнивают её с сетью: `protect`, подписанный текущим хранителем, — это смена второго ключа (F7); `extend` не позже текущего конца — укорочение или снятие замка. Получатели, новые ключи и залог nonce показываются полностью: короткую форму адреса можно подобрать.
- Плательщик показывается, но проверяется только у спасения: его платит D, nonce принадлежит D (§5, §11). Для остальных видов F5 разрешает основному ключу платить за второй.
- Комиссия в сводке: 5000 × подписантов + ceil(лимит × цена / 10⁶) = 10 600 лампортов для protect, 15 600 для спасения.
- Прокси воркера отправляет только после `inspectTransaction` и `verifyAllSignatures` и пересылает проверенные байты. Время CPU инспектора в Node около 4–5 мс: замерить в workerd на шаге 3 (лимит бесплатного плана — 10 мс). Замер и оптимизация — D41.

## D24. Подписи и хвост Lighthouse (02.10.2026)

- Хвост Lighthouse допускается в одной форме: новые аккаунты дописаны в конец как read-only non-signer; в заголовке меняется только `numReadonlyNonSignerAccounts`; исходные инструкции и индексы не меняются; программа Lighthouse — аккаунт, добавленный хвостом. Хвост может ссылаться на существующие аккаунты с теми же ролями: это значит, что мы доверяем Lighthouse их флаги signer. Вернуться к этому после матрицы кошельков и проверки, кто может обновлять программу Lighthouse.
- Если Phantom пересортировывает read-only аккаунты при дописывании хвоста (так делают kit и web3.js), такой хвост сейчас отклоняется. Матрица кошельков на шаге 3 покажет; если так, правило переписывается на сравнение по адресам и ролям.
- `compareSignedMessage` заменён на `checkSigningStep(sent, returned)`. «Первый подписывающий» значит, что транзакция пришла без подписей; флагу больше не доверяем. Подписи, которые были на входе, должны вернуться побайтно; новые подписи должны проверяться. Коды: `message-changed`, `tail-not-first-signer`, `tail-adds-signer`, `signature-changed`, `invalid-signature`, `verification-unavailable`. Legacy, превращённый в v0, — `message-changed`.
- `verifyAllSignatures` сообщает сначала «проверка недоступна», потом неверные подписи, потом отсутствующие. Сайту нужен Ed25519 в Web Crypto.

## D25. Мониторинг: события (02.10.2026)

- `diffSnapshots` выдаёт каждый тип не больше одного раза за вызов:
  - DEACTIVATED — у аккаунта появилась эпоха снятия, которой не было;
  - DELEGATION_CHANGED — другой валидатор, новая эпоха активации или отменённое снятие; первая делегация инициализированного аккаунта тоже считается;
  - LOCKUP_CHANGED — `extended`, `shortened`, `removed` (новый конец не позже текущего момента, в том числе 0), `custodian-changed`, можно несколько сразу;
  - EXPIRED — конец замка не менялся и попал в интервал (`previous.checkedAt`, `context.checkedAt`]; замок, который держит эпоха, EXPIRED не даёт;
  - ACCOUNT_CLOSED — аккаунта нет или он больше не декодируется, приходит один.
- Не события: рост баланса (награды), смена эпохи замка (в D1 нет колонки).
- `DiffContext.checkedAt` обязателен и равен тому значению, которое воркер запишет для этого чтения: так EXPIRED не теряется и не дублируется.
- Повторный поиск аккаунтов withdrawer: после DEACTIVATED, STAKER_CHANGED, BALANCE_DECREASED (§8) и ACCOUNT_CLOSED (Split всего баланса закрывает исходный аккаунт). Искать по сохранённому (старому) withdrawer. После ACCOUNT_CLOSED строка помечается закрытой и больше не сравнивается.
- Тексты тревог и напоминаний (`formatAlert`, `formatReminder`, `reminderDue`) живут в core: обычный текст, без слов custodian/withdrawer/staker, кнопка ведёт на путь сайта, домен добавляет воркер. Напоминания начинаются заново после продления, сбрасывать `last_reminder_days` не нужно. Отложено: текст тревоги для замка, который держит эпоха, пока считает замок действующим только до unix-срока.

## D33. HttpChain: таймауты и повторы (02.10.2026)

- Целые числа из JSON читаются как bigint, лампорты точные.
- Попытка в браузере ждёт 30 с. Это дольше бюджета воркера на чтение (3 × 8 с + 250 + 500 мс = 24,75 с), неравенство держит тест.
- Повтор до двух раз (паузы 500 и 1500 мс) только если ответ воркера не пришёл (TypeError, оборванное тело, таймаут) или пришёл HTTP 503. Cloudflare отвечает 503, когда воркер превысил лимит ресурсов, так что холодный старт сверх 10 мс CPU (D41) лечится повтором. 502, 504, 429 и ошибки JSON-RPC не повторяются. Худшее ожидание одного чтения около 92 с.
- Отправка повторяет только те же байты; AlreadyProcessed — успех с подписью, посчитанной локально. Если отправка упала после попытки без ответа, HttpChain один раз читает `getSignatureStatuses` и считает отправку успешной, если сеть знает подпись. Так ловится nonce-транзакция, которая уже прошла: её повтор падает с BlockhashNotFound, а не с AlreadyProcessed.
- Высота блока берётся из `getEpochInfo`, Clock — через `getAccountInfo` по sysvar, ответ `/api/stake-accounts` разбирает `stakeAccountsFromJson` из core.
- `waitForConfirmation` возвращает confirmed, failed, expired или timeout: опрос раз в 2 с, не дольше 120 с, отмена через AbortSignal, перед expired статус перечитывается. Каждый круг чтений обрывается по сроку и по отмене. HttpChain сигнал не принимает: брошенное чтение игнорируется, его ограничивают таймауты транспорта.

## D34. Кошельки через Wallet Standard (02.10.2026)

- В список попадает кошелёк с `standard:connect`, `solana:signTransaction` (legacy) и цепочкой текущей сборки (`solana:devnet` или `solana:mainnet`).
- Подпись — один вызов `solana:signTransaction` на все транзакции, с объектом аккаунта, который кошелёк отдаёт сейчас.

Запрос, чей `signal` отменён, сразу освобождает очередь; если окно кошелька на самом деле ещё открыто, следующий запрос получит `WalletBusyError`. Отказ пользователя приходит с кодом 4001.

## D35. Слоты и известные вторые ключи (02.10.2026)

## D39. Воркер: /api/rpc и /api/stake-accounts (02.10.2026)

- Метод ищется через `Object.hasOwn`, параметры каждого метода проверяет строгая схема zod (`rpc-params.ts`). Тело до 32 КиБ, Content-Type только JSON, batch запрещён.

Префиксы сообщений экспортирует core (`INSPECTOR_REFUSAL_PREFIX`, `SIGNATURE_REFUSAL_PREFIX`), так что воркер и сайт не разъедутся.
- simulateTransaction и sendTransaction идут только после `inspectAndVerifyTransaction`, дальше уходят ровно проверенные байты.

- Адреса из ответа upstream проверяет `isAddressText`: тот же ответ, что у `isAddress` из kit, но одно преобразование base58 вместо трёх.

Что поменяли, не ослабив проверок:
- кодеки kit строятся один раз на модуль, включая декодер стейка и кодировщики инспектора;
- каноничность байтов проверяется сравнением с ожидаемым размером, без перекодирования. Это точно только вместе с запретом сообщения без инструкций: декодер kit не читает отсутствующий счётчик в конце, и такое сообщение проходило по размеру. Инспектор теперь отвечает на пустое сообщение `malformed`, а не `bad-layout`;
- сообщения сравниваются по полям (`isSameMessage`); инспектор сравнивает скомпилированное сообщение сборщика (`compileActionMessage`) до кодирования;
- `inspectAndVerifyTransaction` декодирует один раз и проверяет каждую подпись один раз (`signatureCheckOf`).

Каждое сокращение сверено со старой проверкой: около 6000 правок настоящих сообщений по одному байту и длине, 20 000 случайных строк адресов, комбинированная функция против двух раздельных.

Лимит бесплатного плана — 10 мс CPU на запрос. Тёплые пути в него укладываются, холодный изолят нет: время уходит на первую компиляцию кодеков kit. Решение за владельцем (§8, §15): Workers Paid за 5 долларов в месяц или редкие отказы на холодном изоляте, которые браузер чаще всего скроет повтором 503 (D33). Прогрев при загрузке модуля не сделан: неизвестно, относит ли Cloudflare это время к первому запросу. Ещё около 0,2 мс можно снять, если брать ключи из сырых байтов, но это лишний самописный код в ядре безопасности. JSON-ревайвер gPA стоит около 10 %, зато держит u64 лампортов точными; оставили.

## D47. Механизм подписи (05.10.2026)

Общий для защиты, вывода, продления и спасения: `apps/web/src/signing`.
- Чистый редьюсер `machine.ts` (все переходы покрыты тестами), драйвер `session.ts` без React, хук `use-signing-session.ts` (сессия создаётся в эффекте и переживает двойной эффект StrictMode), панель `SigningPanel.tsx`.
- Кто подписывает, берётся только из сводок инспектора по текущим байтам: требуемые подписанты минус уже подписавшие. Порядок задаёт core `signingOrder`: кошелёк, который дописывает хвост Lighthouse (сейчас только Phantom, `TAIL_FIRST_WALLETS`), первым и только на неподписанной транзакции; затем плательщик комиссии; затем остальные. Выбранный порядок («Start again with … signing first») держится и в следующих этапах.
- Несколько аккаунтов: каждому своя транзакция, все транзакции этапа подписываются одним запросом к каждому кошельку. Не больше 10 за запуск (лимит прокси, D40). Кошелёк, который вернул не столько транзакций, сколько просили (`WalletBatchUnsupportedError`), — предложение подписывать по одной.
- После каждой подписи `checkSigningStep` по всем транзакциям этапа; первое расхождение останавливает весь этап, ничего не отправляется. После последней — `verifyAllSignatures`, затем отправка сама, без отдельной кнопки: экран сводки и одобрение в каждом кошельке и есть подтверждение.
- Отказ кошелька: «Try again» просит тот же кошелёк подписать те же байты, прежние подписи сохраняются.
- Блокхэш: если до первой подписи осталось меньше 60 блоков, этап собирается заново и пользователь смотрит новые сводки. Истёк между подписями — «Sign again», каждый кошелёк одобряет заново.
- Ошибки отправки: однозначные (в том числе 429, когда предыдущая попытка получила ответ) — `failed`; сеть, неизвестное, AlreadyProcessed и 429 после попытки без ответа (`SendOutcomeUnknownError`) — ждём статус до истечения блокхэша. Пока отправленная транзакция может попасть в сеть, её не собирают заново.
- Успех засчитывается только после чтения сети: core `actionApplied` по самому аккаунту, до трёх перечитываний через 2 с (отстающий узел).
- Каждое ожидание объяснено и имеет выход: фаза `starting` (чтение высоты блока перед просьбой к кошельку, `connect` после переключения аккаунта), подпись, отправка, подтверждение, проверка — везде «Stop waiting».
- Остановка после уже прошедшего этапа (`finish`) показывает и записывает то, что прошло, а не «Nothing was sent».

## D49. POST /api/watch (05.10.2026)

- Тело `{ accounts }`: от 1 до 20 разных адресов, не нулевой ключ. Воркер сам читает аккаунты и Clock одним `getMultipleAccounts` (Clock первым) и решает по core `watchVerdict`: замок действует по дате (не по эпохе), второй ключ — не сам основной ключ и не нулевой, конец замка не дальше 400 дней. Это строже §8 («с действующим замком»): замок, который снимает сам основной ключ, ничего не защищает (D14), а старые замки по эпохе и многолетние вестинги в мониторинг не нужны.
- Строки только добавляются: живая строка не перезаписывается никогда, закрытая оживает только по более свежему слоту. Иначе вор с основным ключом снял бы стейк с делегирования, вызвал `/api/watch`, снимок освежился бы, и тревога DEACTIVATED не ушла бы. Это отступление от §8 («записать или обновить строку»).
- Ответ по каждому адресу в порядке запроса: `watched`, `already-watched` или `rejected` с причиной. Лимит частоты `WATCH_RATE_LIMIT` — 10 запросов за 60 с на IP. Потолка на число строк нет: его можно было бы забить бесплатно и закрыть дорогу настоящим пользователям; нагрузку разносит курсор монитора.

## D54. Проход мониторинга (05.10.2026)

- Один Cron Trigger `*/2 * * * *` на окружение. Проход: аренда и загрузка, пачки чтения (каждая коммитится сразу), суточная часть, отправка в Telegram (коммит сразу), повторный поиск, финиш.
- Аренда в `meta` (`pass_lease`): TTL 110 с, мягкий срок прохода 60 с, все записи в `meta` огорожены id прохода, `controller.noRetry()`. Проходы не накладываются; умерший проход (обычно лимит CPU) виден следующему, админ получает тревогу.
- Отметка `last_pass_at` пишется последним оператором и только при успехе. Не успех: чтение пачки не удалось, genesis не совпал, Telegram отверг токен (401/404) или `SITE_ORIGIN` неверен, любое исключение. Отложенная работа (лимит, срок) успеху не мешает: курсор продолжит со следующего прохода.
- Ровно 99 строк на бесплатном плане: страница полная, следующий проход читает пустую страницу и сбрасывает курсор, так что такие строки проверяются раз в 4 минуты. Больше 99 — круг из нескольких проходов плюс один короткий.

## D55. Лимиты прохода (05.10.2026)

- Документация Cloudflare говорит о 50 подзапросах на вызов и отдельно о 50 запросах к D1 на бесплатном плане, и неясно, как считается batch. Поэтому один общий счёт: каждая попытка fetch плюс каждый оператор D1 (batch из n — это n), не больше 48. Резерв: финиш и одна тревога админу.
- Пресеты `MONITOR_PLAN` (`free`/`paid`, переменная wrangler): на free одна пачка `getMultipleAccounts` (Clock + 99 аккаунтов), 20 декодирований, 3 поиска, ответы поиска до 120 000 символов за проход; на paid пять пачек (§8), 500 декодирований. Сейчас везде `free` (решения по Workers Paid нет).
- Строка `accounts` пишется только при изменении: бесплатная D1 даёт 100 000 записанных строк в сутки, тихий проход пишет 3 строки `meta`.

## D56. Быстрый путь по отпечатку (05.10.2026)

- Отступление от §4: смещения байтов используются не только в фильтрах getProgramAccounts. Отпечаток — base64 тех байтов, которые читает `diffSnapshots` (232 символа из 268; без младших байтов суммы стейка, `credits_observed`, warmup и флагов, которые меняют награды). Отпечаток тот же и лампорты не упали — декодировать не нужно, событий не будет. Декодирование, когда оно нужно, идёт через сгенерированный клиент.
- Тест-свойство: 10 000 случайных пар и каждое поле по отдельности; когда `canSkipDecode` говорит «можно», `diffSnapshots` пуст. Отпечаток требует ровно один `=` в конце: 268 символов могут быть и 199, и 201 байтом.
- `checked_at` — время последней записи строки по часам кластера (`max` с прошлым значением), так интервалы EXPIRED смежны.

## D57. События ровно один раз (05.10.2026)

- События вставляются и строка обновляется в одном batch с CAS по версии строки `(slot, checked_at)`; UNIQUE остаётся страховкой. Слот события — слот чтения.
- Ответ чужого кластера не закрывает аккаунты: если хоть один аккаунт прочитан как пропавший, воркер сверяет genesis hash того самого узла, что ответил (основного или запасного), один раз на узел за проход. Это строже спецификации шага 5 (там проверка шла от половины пачки и на любом узле). `GENESIS_HASH` переехал в core.
- Отстающий узел (слот ответа меньше слота строки): строку пропускаем, ничего не пишем.

## D58. Напоминания (05.10.2026)

- Напоминания — строки `events` с типом `REMINDER_30 | _14 | _7 | _3 | _1`, их считает суточный проход (первый после 06:00 UTC, отметка `daily_day`). EXPIRED выдаётся в любом проходе (D25).
- При вставке строки `last_reminder_days` засевается текущим порогом: задним числом напоминание не приходит. Новый конец замка сбрасывает напоминания; смена второго ключа с той же датой — нет. Напоминание, устаревшее до отправки (замок продлили), закрывается без отправки.

## D59. Повторный поиск по паре ключей (05.10.2026)

- Отступление от §8: заново ищем не по одному withdrawer, а по паре (main key, second key): `memcmp 44` + `memcmp 92`. Split копирует замок, поэтому пара ловит каждый Split. Поиск по одному withdrawer у крупных адресов без предела по CPU на бесплатном плане и каждый день заново декодировал бы их незапертые аккаунты. Замки с другим вторым ключом попадают под наблюдение через `/api/watch`.
- Очередь пар в `meta.rescan_queue`, до 1000; срочные пары (после DEACTIVATED, STAKER_CHANGED, BALANCE_DECREASED, ACCOUNT_CLOSED) — первыми и переживают неудачный проход. Пара, отложенная лимитом, хранит место остановки и продолжает после него. Без живых строк проход читает один Clock и всё равно ведёт поиск.
- Найденный аккаунт с действующим замком той же пары берётся под наблюдение без событий; закрытая строка оживает только по более свежему слоту.

## D60. Доставка в Telegram (05.10.2026)

- Прогресс хранится на привязке: `alert_links.last_event_id`; новая привязка начинает с последнего события. chat id живёт только в `alert_links`, поэтому `/stop` действительно его забывает.
- Одно сообщение на чат за проход, до 5 тревог и одна кнопка-ссылка на `SITE_ORIGIN`. Когда окно из 100 ожидающих событий полное, сообщение закрывает всю долю чата строкой «And N more alerts …», чтобы один занятый чат не задерживал остальных.
- Ответы Telegram: 403 удаляет все привязки чата; 400 — чат пропущен, прогресс сдвинут; 401/404 — проход неуспешен; 429 — отправка ждёт следующего прохода; 5xx и таймаут — повтор в следующем проходе. Событие, не доставленное за 7 дней, закрывается. Повтор сообщения возможен только при сбое между отправкой и коммитом (at-least-once).
- Миграция `0003_pending_index.sql`: индекс ожидающих событий по `id`, иначе выборка читала бы всю историю событий.

## D61. Telegram-бот и ссылка (05.10.2026)

- Вебхук: секрет из заголовка сравнивается через SHA-256 и `crypto.subtle.timingSafeEqual` до чтения тела и до D1; ответ боту — прямо в теле ответа на вебхук (исходящего запроса нет); мусор и тело больше 64 КиБ — 200 `{}`, чтобы Telegram не повторял; ошибка D1 — 500, чтобы повторил. Лимит частоты на чат (`TELEGRAM_RATE_LIMIT`, 20 за 60 с). `my_chat_member` kicked/left отвязывает. Не больше 20 кошельков на чат.
- `/start` пишет в D1; на все чаты вместе не больше 1000 таких записей в сутки (`meta.link_writes`), иначе два чата могли бы съесть общую квоту записей D1. Сверх лимита `/start` вежливо отказывает, `/status` и `/stop` работают.
- `GET /api/telegram/link?wallet=` отвечает 302 на `t.me/<бот>?start=<адрес>`. Имя бота (`TELEGRAM_BOT_USERNAME`) и `SITE_ORIGIN` лежат рядом с секретами (`secrets.required`), а не в `vars`: `wrangler types` даёт vars литеральные типы, а CI проверяет свежесть типов. Значения меняются без пересборки сайта.
- Секреты Telegram стали обязательными (поправка к D9 и D40): первый деплой идёт с `--secrets-file`.

## D64. Страницы /withdraw и /extend (05.10.2026)

- `/withdraw/:account` показывает действие по статусу: active или activating — Deactivate (подписывает основной ключ как staker); deactivating — отсчёт до конца эпохи; inactive — Withdraw всего баланса на основной ключ, подписывают основной и второй ключ. Поля получателя и суммы нет. Предупреждение «If your main key may be compromised, do not withdraw to it. Use Rescue» — до подписи.
- Если staking-ключ чужой (сервис или вор), Deactivate не предлагается, есть ссылка на спасение. Замок самого основного ключа или «ничей» — отказ с объяснением.
- Запасной путь: второй ключ снимает замок, затем основной ключ выводит один, с предупреждением, что это открывает окно для вора. Для замка по эпохе он скрыт.
- `/extend/:account` (F5): только более поздние сроки и снятие замка; снятие — с обязательной галочкой. Плательщика выбирает план: второй ключ, если `canPayFee` по его балансу, иначе основной ключ платит и подписывает вместе с ним. Замок по эпохе не трогаем. Страница работает во встроенном браузере кошелька (одна подпись).

## D66. Ключ в слоте и подтверждение на экране подписи (05.10.2026)

- `KeySlot expected`: когда механизм подписи ждёт конкретный адрес, слот принимает только его. Если в слоте уже другой аккаунт, слот просит отключиться и подключиться этим аккаунтом.

## D67. Nonce и подпись по ссылке в механизме подписи (05.10.2026)

- План может нести `nonce` (транзакции на durable nonce) и `remote` (подписанты, которые подписывают по ссылке). С nonce этап — одна транзакция: каждая сдвигает nonce.
- Плательщик всегда локальный и владеет nonce-аккаунтом; локальные подписи идут первыми, потом показывается ссылка. Её id известен: это подпись плательщика.
- Фаза `link`: ожидание по id без `searchTransactionHistory` — стейк-аккаунт и nonce-аккаунт читаются одним запросом плюс статус подписи. Опрос через 3 с, шаг ×1,5 до 15 с, 30 минут; при возврате на вкладку — сразу.
- Отставший узел: значение nonce, которое этот экран уже отправил или выдал ссылкой, не используется снова (`usedNonces`); чтение nonce из более старого слота не считается доказательством, что ссылка использована.

## D68. Отмена ссылки — закрытие nonce-аккаунта (05.10.2026)

Расхождение с §6 («сдвинуть nonce»): одиночный AdvanceNonce не входит в формат инспектора, а новый вид транзакции потребовал бы правок в инспекторе, сборщиках и прокси. Закрытие — уже существующая транзакция `nonce-close`, залог возвращается. Пока ссылка открыта, «Try again» не предлагается: повтор занял бы тот же nonce.

## D69. Правила /cosign (05.10.2026)

- Ссылки только на protect, withdraw и rescue. Nonce принадлежит плательщику, плательщик ожидаемый и уже подписал, хотя бы одной подписи не хватает. Получатель вывода — только основной ключ (строже красного предупреждения §9; вопрос владельцу).
- Protect поверх действующего замка отклоняется: иначе вор с основным ключом мог бы прислать держателю второго ключа ссылку, которая меняет хранителя и ставит раннюю дату. Сводка такой транзакции предупреждает, что замок кончится раньше.
- По сети: изменение уже есть — Done; nonce не совпал — ссылка использована или отменена; withdrawer не основной ключ — ссылка устарела.
- Обязательная галочка для withdraw и rescue. Все оставшиеся подписи — на этом устройстве, без передачи ссылки дальше.
- Первое устройство проверяет те же правила (core `cosignLinkProblem`) до того, как показать ссылку: Stakeward не выдаёт ссылку, которую сам откажется принять.

## D70. Спасение /rescue (05.10.2026)

- Один второй ключ за прогон, до 10 аккаунтов. Порядок: без замка, затем по дате конца замка (замки по эпохе после датированных), затем по сумме.
- Аккаунты без действующего замка тоже переводятся: программа тогда не проверяет хранителя. Замок самого основного ключа или «ничей» не переводится.
- Новый кошелёк D платит (проверка баланса до старта), владеет nonce-аккаунтом; спасение всегда на nonce, даже если все три ключа в одном браузере (F4.3). Каждый аккаунт — своя транзакция AuthorizeChecked(Staker) + AuthorizeChecked(Withdrawer), подписывают A, D и K.
- После: повторный поиск аккаунтов основного ключа (новые после Split), предложение делегировать снова (подписывает D) и закрыть nonce-аккаунт, ссылка на Telegram для нового кошелька.

## D84. /api/stats считает не чаще раза в 10 минут (06.10.2026)

Подсчёт читал все отслеживаемые строки на каждый запрос. Бесплатная D1 даёт 5 млн прочитанных строк в сутки на всё, включая мониторинг: при 20 запросах в минуту с IP и 1000 строк один клиент читал бы 28,8 млн в сутки и остановил бы тревоги. Теперь подсчёт хранится в `meta.stats_cache` 10 минут (не больше 144 подсчётов в сутки, кто бы ни спрашивал); `alerts_sent` читается каждый раз (одна строка); `now` ответа — время подсчёта. Нечитаемая или «будущая» запись считается заново.

Открытый вопрос владельцу: любой может поставить под наблюдение чужой замок через `/api/watch`, поэтому «accounts locked» — это аккаунты, которые видит Stakeward, а не «защищённые через Stakeward». Для заявки честнее добавить число уникальных основных ключей или аккаунтов с включёнными тревогами.
