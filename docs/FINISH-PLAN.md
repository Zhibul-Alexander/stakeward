## 2. Автоспасение (10–11.10)

Идея: во время защиты пользователь заранее подписывает транзакцию спасения на durable nonce, воркер хранит её и отправляет по тревоге. Отправить её может кто угодно, но результат всегда один: стейк уходит на собственный кошелёк пользователя D.

- Включается по желанию на шаге защиты: «Auto-rescue to a new wallet». Нужен кошелёк D из третьей seed-фразы.
- На каждый стейк-аккаунт свой nonce-аккаунт. Authority — D, платит тоже D (около 0,0015 SOL залога, он возвращается).
- Транзакция: AdvanceNonce, Compute Budget, AuthorizeChecked(Staker → D), AuthorizeChecked(Withdrawer → D). Подписывают D (он же плательщик), A и K. Формат тот же, что у ручного спасения.
- `POST /api/auto-rescue`: инспектор принимает только вид rescue, все подписи на месте и проверены, новый владелец совпадает с плательщиком и с authority nonce, симуляция проходит. Таблица D1 `auto_rescue` (миграция). Отключить: D сдвигает nonce, и сохранённая транзакция умирает, плюс удаление строки.
- Триггеры в cron: DEACTIVATED, STAKER_CHANGED, DELEGATION_CHANGED, BALANCE_DECREASED (Split). Отправка один раз; итог перечитывается из сети; в Telegram уходит «Auto-rescue done: stake now belongs to D».
- Ложное срабатывание безвредно: стейк переходит на собственный кошелёк D.
- Честные ограничения, которые проговариваем:
  - аккаунт, который вор отделил через Split, транзакцией не покрыт. Он остаётся под замком, его спасают руками;
  - вор может слить через Merge два своих аккаунта с одинаковым замком. Тогда транзакция падает, но SOL остаются под замком;
  - смена второго ключа (F7) делает транзакцию недействительной, её нужно подписать заново.
- §2.6 в новой редакции: «Воркер не собирает и не подписывает транзакции. Он может хранить и отправить полностью подписанную пользователем транзакцию спасения, которая переводит стейк только на кошелёк пользователя». Взлом воркера даёт не больше, чем «спасти стейк раньше времени».
- Тесты: сборщик и инспектор в core; приём и отказы `/api/auto-rescue` в воркере; cron отправляет ровно один раз; сценарий на LiteSVM «защита + автоспасение → вор снимает стейк с делегирования → проход cron → staker = withdrawer = D».

## 3. Переводы (11.10, после заморозки текстов)

- Каркас: `src/i18n/{en,zh,es,pt-BR,ru,ka}.json`; язык берётся из `?lang=`, затем из `localStorage`, затем из `navigator.language`. Переключатель в шапке, `<html lang>` подставляется. Даты через `Intl` с локалью.
- Глоссарий ролей и статусов на каждый язык (Main key, Second key, New wallet, Protected, Rescue…), чтобы на экране подписи не было разнобоя.
- Шрифты: подмножество Noto Sans Georgian кладём в репозиторий. Для китайского берём системные шрифты: CJK-шрифт весит мегабайты.
- Без перевода остаются команды CLI в карточке восстановления, адреса и Telegram-тревоги (тревоги на английском, это записать).
- Тесты: у каждого языка тот же набор ключей и те же плейсхолдеры, глоссарий соблюдается, правило про custodian/withdrawer работает в каждом языке, e2e открывает основные маршруты на 360 px в каждом языке: без вылезающего текста и с чистым axe.
- Вычитка носителями: ka — Superteam Georgia, ru — владелец, остальные языки — машинный перевод, это сказано в FAQ.

## 4. Демо «кнопка спиздить» (10–11.10)

- `pnpm demo:steal` на devnet с ключом A из `.keys/`. Вор пробует вывести SOL и переписать на себя право вывода. Без замка это проходит, с замком сеть отвечает `LockupInForce`. Ключ живёт только в скрипте, на сайт он не попадает (§2, §11).
- Сценарий записи: сначала стейк без защиты → «спиздили»; затем новый стейк, защита с автоспасением → вор снимает с делегирования и пытается вывести → сеть отказала → тревога в Telegram → автоспасение уже сработало: стейк на кошельке D. Для кадра «деньги на D» берём неделегированный аккаунт: после спасения D выводит сразу.
